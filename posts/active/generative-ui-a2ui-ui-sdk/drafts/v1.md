# Three Jobs Called "Generative UI": Where to Draw the Boundary Between Agents and Interfaces

On 11 November 2026, Google called A2UI 1.0 "the first stable version" of its open protocol for generative UI. The next day, Vercel Labs introduced UI SDK, "a library of behaviors for agents to build the next generation of user interfaces."

Both put an agent in front of an interface. They do different things.

The phrase "generative UI" has stretched to cover both, along with json-render, assistant-ui, Tambo, the Vercel AI SDK, MCP Apps and AG-UI. Read the documentation for each and the vocabulary overlaps in confusing ways. This piece separates three jobs hiding under one name, and argues that in each of them the design decision that matters is the boundary you draw around the agent, not the model behind it.

## The claim

"Generative UI" now names at least three jobs: an agent can emit an interface, write one, or operate one. In each, the thing worth designing is the boundary the developer owns. For constrained emitters it is a component catalog. For unconstrained emitters it is a sandbox. For an agent acting on a live page it is a permission layer. That boundary, not the model, is where reliability, accessibility and brand safety get settled.

## Emit: the agent produces the interface

In the first job, the agent produces what appears on screen, at runtime. There are two families, and they differ in how much freedom the agent gets.

### Constrained emitters

A2UI is the clearest example. Google's announcement puts it plainly: the agent describes what to show, and every app draws the UI with its own native components. The protocol's homepage is more specific. It "streams declarative JSON data with two-way bindings — never executable code."

The shape of that data is simple. A message is a JSON object with a `version` field. An agent creates a surface, sends components as a flat list that refer to each other by ID, with one component marked `root`, and updates a data model that components bind to. Bindings use a path syntax such as `{"@path": "/reservation/destination"}`. Buttons raise actions that carry resolved values back to the agent.

[SAMPLE: copy a complete `createSurface` message with a bound button action from https://a2ui.org/concepts/messages/ before publishing.]

What the agent can place is set by a catalog, which the A2UI docs call "a collection of components and functions that acts as a contract between an agent and a renderer." Each component is a JSON Schema. The basic catalog ships 18 components and 14 functions, and an app can adopt it, restyle it, extend it or replace it. The homepage states the consequence: "Agents place only components you registered."

Functions carry permissions too. A function declares who may call it (`rendererOnly` is the default) and whether it needs a user gesture. Per the docs, that second flag exists so a message from an agent cannot trigger navigation without the user's intent.

Several other projects take the same approach with different packaging.

json-render, from Vercel Labs, describes itself this way: "AI generates interfaces from natural language prompts, constrained to components you define." You declare a catalog with Zod schemas, the model emits a flat JSON spec, and renderers turn it into UI for React, Vue, Svelte, Solid, React Native, PDF, email and more. This is the catalog section of its README quick start:

```tsx
import { defineCatalog } from "@json-render/core";
import { schema } from "@json-render/react/schema";
import { z } from "zod";

const catalog = defineCatalog(schema, {
  components: {
    Card: {
      props: z.object({ title: z.string() }),
      description: "A card container",
    },
    Metric: {
      props: z.object({
        label: z.string(),
        value: z.string(),
        format: z.enum(["currency", "percent", "number"]).nullable(),
      }),
      description: "Display a metric value",
    },
    Button: {
      props: z.object({
        label: z.string(),
        action: z.string(),
      }),
      description: "Clickable button",
    },
  },
  actions: {
    export_report: { description: "Export dashboard to PDF" },
    refresh_data: { description: "Refresh all metrics" },
  },
});
```

*From the json-render README (Apache-2.0), read 21 November 2026.*

assistant-ui has the model emit a flat JSON tree through a `present` tool, with 35 default components and Zod schemas for custom ones. Tambo registers components with a Zod `propsSchema`. The Vercel AI SDK takes the smallest step: "Generative UI is the process of connecting the results of a tool call to a React component." The model picks a tool, and your code decides which component renders its result.

### Unconstrained emitters

MCP Apps goes the other way. It is an extension to the Model Context Protocol, and its specification is marked "Stable (2026-01-26)." A tool declares a `ui://` resource, and the host renders the HTML it contains in a sandboxed iframe that talks to the host with JSON-RPC over `postMessage`. The agent, or the tool author, is not picking from a catalog. It is shipping an interface.

The control moves elsewhere. The specification requires the sandbox and the host to have different origins, requires hosts to build a content security policy from the domains an app declares, and sets a restrictive default (`default-src 'none'`, `connect-src 'none'`) when none is declared. The docs list Claude, Claude Desktop, VS Code GitHub Copilot, Microsoft 365 Copilot, Goose, Postman, MCPJam and Archestra.AI as supporting hosts.

### Transport is a separate question

AG-UI belongs in a different box. Its own documentation says "AG-UI is not a generative UI specification." It is an event-based protocol that connects an agent to a front end, and it carries the formats above. Its repository now says "AG-UI 1.0 is here," with "a stable, frozen specification backed by a JSON Schema."

## Write: the agent produces the code

The second job happens before anyone opens the app. An agent writes components, and the question is what it builds them from.

UI SDK is aimed at this. It is a headless library of behaviors: keyboard navigation, focus, selection, dismissal, popups, drag and drop, and the ARIA they need, in a core package with adapters for React, Vue, Svelte, Solid and Web Components. There are 55 unstyled React components built on it. The agent composes them.

It also ships a skill for coding agents, installed with:

```
npx skills add vercel-labs/ui --skill ui-sdk
```

*From the UI SDK README.*

The skill is a workflow, not a prompt. It tells an agent to read the installed docs first, choose behaviors, define a primitive, render it, and test it. Its rules are the unglamorous kind that decide whether generated UI is usable: name every control with a label, never generate ids, key lists by value or id rather than index, and don't hand-roll `role` attributes for components the library already ships. The work finishes with typechecking, tests, and a report of each command's exit code.

Here the boundary is the set of tested behaviors and the review that follows. The agent writes code that a person can read, run and test before a user ever sees it.

## Operate: the agent acts on an interface that already exists

The third job gets the least attention, and UI SDK covers it too. Its "Connect an Agent" feature lets an agent read a live page and act on it.

```tsx
import { createAgent } from "@ui-sdk/react/agent"

const agent = createAgent()

export { agent }
```

*From the UI SDK docs, Connect an Agent.*

A call to `agent.snapshot()` returns the components on the page, with the actions each one supports:

```json
[
  {
    "ref": "c1",
    "component": "input",
    "label": "Project name",
    "value": "Apollo",
    "actions": ["setValue", "clear"]
  }
]
```

The agent then acts on one of them:

```tsx
const result = await agent.act({
  steps: [{ ref: "Project name", action: "setValue", args: ["Atlas"] }],
})
```

*From the UI SDK docs, Connect an Agent.*

The same three tools (`snapshot`, `act` and `query`) can be offered to "the agent built into a browser" through WebMCP, using the browser's `document.modelContext` API. Registration does nothing in a browser that lacks it, and the docs don't say which browsers do.

Nothing here generates a new interface for an end user. The docs describe an agent reading and operating components that are already rendered. That is a different job, with a different risk: an agent that can press buttons on your page.

The permission layer is the boundary, and the documentation spells out its mechanics. An `allow` callback runs before each step and can refuse it. It can return a promise to ask the person, and a step fails if nobody answers within five minutes. A control marked `data-agent-confirm` always needs a person:

```tsx
<Button
  data-agent-confirm="Charges $20 to your card for 1,000 credits"
  onClick={buyCredits}
>
  Buy credits
</Button>
```

*From the UI SDK docs, Permissions.*

`data-agent-hidden` removes a component from what the agent can see. `data-agent-secret` redacts a value, and password, card and one-time-code fields are treated as secret without a mark. The docs also warn, with unusual frankness, that "an `allow` that returns `true` without reading `step.confirm` answers yes for the person."

## The boundary map

Put the three jobs side by side and the pattern is that each has a different boundary, and each boundary has a different edge.

| Job | Examples | Where the boundary sits | What it limits | What the docs say it does not cover |
|---|---|---|---|---|
| Emit, constrained | A2UI, json-render, assistant-ui, Tambo, AI SDK tool UIs | Component catalog and function permissions | Which components can appear | Content: an agent can still choose any registered component and send any values; the A2UI pages describe no semantic check |
| Emit, unconstrained | MCP Apps | Sandbox, content security policy, auditable messages | What the HTML can reach | Depends on the host enforcing the specification |
| Write | UI SDK skill and behaviors | Tested behaviors, tests, code review | What the agent builds from | Anything the tests and review miss |
| Operate | UI SDK `createAgent`, WebMCP | `allow`, confirmations, hidden and secret marks | Which actions run | Visibility: components remain in `snapshot()`, and finding one can open a section before the action is checked |

Two caveats about the table. The last-column cells for "Emit, unconstrained" and "Write" are my reading, not statements from the documents. The last cell for "Operate" is the UI SDK docs' own description of what `allow` covers.

Vendors have drawn their own maps. CopilotKit's "generative UI spectrum" runs from controlled to declarative to open-ended, with MCP Apps as its own band. AG-UI's docs name static and declarative. One community list splits constrained from unconstrained. Those axes measure how much freedom the agent has. The axis here is different: who is doing what, and so where the risk sits. The two views combine without conflict. Treat the vendor pages with care, though: they are not independent, and one of them announces three pillars while showing four bands.

## Trade-offs

Constrained emission buys predictability and costs expressiveness. If the catalog lacks a component, the agent cannot invent one. That is the point, and also the ceiling.

Unconstrained emission buys the opposite. An app can ship anything, and the trust moves from the catalog to the sandbox. A sandbox limits what the code can reach. It says nothing about whether the interface it renders is accurate or accessible.

Writing code with an agent is the familiar kind of risk, and it comes with the familiar controls. The cost is that the check happens at review time, so someone has to do it.

Operating a live page is cheap to add and easy to over-trust. Every control the page exposes becomes something an agent can try. A permission layer helps, but the documentation itself says what `allow` leaves open.

All four boundaries limit form or action. None of them judges content. An agent that chooses a registered component and fills it with wrong values has stayed inside every boundary described above.

## Where the claims outrun the documents

Three claims are worth checking before you rely on them.

**"Stable."** A2UI 1.0 is a stable protocol according to Google. The released packages tell a different story: the Python agent SDK was at 0.12.0 on 17 November, a week after 0.11.0, and the command-line tool was at 0.4.0. None of the releases visible on the project's releases page is a protocol release, and the evolution guide says catalogs written for 0.9 "cannot be used directly" with 1.0. The announcement itself says Gemini supports 0.9.1 today, the Jetpack Compose renderer is at 0.9.1, and ByteDance's Lynx renderer supports 0.9 and is adapting. "Stable" describes the protocol's version, not the ecosystem around it.

**"Sensitive values never reach the model."** The announcement makes this claim. The documentation supports part of it: server code can inject data into a surface "directly into the surface without passing them through the model." But button actions send resolved values back to the agent, and `sendDataModel` attaches the full surface data model to every message to the agent that created the surface. The messages page also says the data model "can be updated directly by the language model during generation." The pages don't say whether data sent to the agent's server then reaches the model. Whether a given value reaches the model depends on how you build it, and nothing in the documentation I read turns that into a guarantee.

**"Production."** UI SDK says "UI SDK is in beta, so some APIs may still change," and every release so far is a pre-release, with 0.1.0-beta.13 out on 19 November. The Vercel AI SDK's RSC route to generative UI is "currently experimental," and the docs say to use AI SDK UI for production. Tambo's README opens with "Tambo Cloud is shutting down": the hosted API was due to stop after 31 October 2026. The project remains open source and self-hostable. That is a useful reminder that a catalog-based approach reduces some risk and leaves vendor risk in place.

I found no independent evaluation of the reliability, accessibility or security of generated interfaces for any of these projects. The adoption claims that exist, such as Atlassian bringing A2UI to Jira, are the vendors' own.

## The objection

The three-jobs split may be taxonomy for its own sake. The lines do blur. A2UI can run inside MCP Apps, and its docs say generated HTML and JavaScript can run as an MCP App inside an A2UI surface. json-render ships an MCP Apps integration. AG-UI carries several of these formats. MCP Apps is an official, stable extension of MCP, and it may make most of this distinction moot.

There is also the objection that a catalog or a permission layer is a thin safeguard, easy to misconfigure and silent about content.

Both objections are fair, and neither changes the claim. The jobs differ in what is at risk, even where the projects overlap. A thin boundary is a reason to design and test it, which is the whole argument. And if MCP Apps wins, the boundary that matters will be the sandbox and the host's enforcement of it.

## What to ask before you adopt one

Not a ranking, but a set of questions that apply to any project in this space.

1. **Which job is the agent doing:** emitting, writing or operating?
2. **Where is the boundary, and who owns it?** A catalog you maintain, a sandbox the host enforces, or a permission callback you write?
3. **What does the boundary not cover?** Read the project's own admissions first, as UI SDK's permissions page is a good model of what they look like.
4. **What is claimed, and what is documented?** Check version numbers across the whole stack, not only the headline protocol.
5. **What is the vendor risk?** Who maintains it, and what happens to the hosted parts if that changes?
6. **How will you test accessibility and content, not only structure?** The boundaries above do not.

## Two launches, three jobs

A2UI and UI SDK arrived within a day of each other and share almost no machinery. One describes screens for an app to draw. The other gives agents the parts and the permissions to work with screens. The name that covers both hides which job you are signing up for.

Watch the boundaries, since they will keep moving. A2UI's maintainers are collecting requirements for a 1.1. AG-UI has frozen a 1.0. UI SDK is still shipping betas. Models in these systems change quickly. The boundary you draw is the part you own.
