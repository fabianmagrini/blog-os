# What the Boundary Doesn't Check: Generative UI After A2UI 1.0

On 11 November 2026, Google called A2UI 1.0 "the first stable version" of its open protocol for generative UI. The next day, according to its docs changelog, Vercel Labs introduced UI SDK, "a library of behaviors for agents to build the next generation of user interfaces."

Both put an agent in front of an interface, and both come with controls meant to keep that safe.

[AUTHOR EXPERIENCE: a real moment where an interface an agent produced or operated was wrong while staying inside the rules. If you have none, delete this line.]

This piece asks a narrower question than "which is better": what do those controls actually check? The claim is that every runtime control the field offers (a component catalog, a sandbox, a permission layer) limits what an agent can show or do, not whether what it shows is correct. In the documents read, correctness is left to offline evaluation and to checks you write yourself. So the reliability work that matters sits outside the boundary.

## How this was checked

Everything here comes from each project's documentation and repositories, read on 21 November 2026. Nothing was run first-hand. These projects change weekly, so versions and dates are a snapshot. Two of the four cases below (operating components, and writing code with an agent) are documented by a single vendor's library, so they show one design, not a field.

## Where an agent meets an interface

There are four cases, and each has a different control. They are a map, not the argument.

### The agent generates the interface from a catalog

A2UI describes this as the agent describing what to show while every app draws it with its own components. Its homepage says it "streams declarative JSON data with two-way bindings — never executable code." Messages are JSON with a `version` field. Components arrive as a flat list that refers to itself by ID, bindings use paths such as `{"@path": "/reservation/destination"}`, and buttons send actions back to the agent with resolved values.

What can appear is set by a catalog, which the docs call "a collection of components and functions that acts as a contract between an agent and a renderer." Each component is a JSON Schema, and the homepage puts the consequence plainly: "Agents place only components you registered." Functions carry permissions too: who may call them, and whether a user gesture is required, so that an agent message cannot trigger navigation on its own.

The control exists to stop the model picking something the app did not allow. json-render, assistant-ui and Tambo work the same way with Zod schemas. json-render's README says "AI can only use components in your catalog." Here is the start of its catalog:

```tsx
const catalog = defineCatalog(schema, {
  components: {
    Card: {
      props: z.object({ title: z.string() }),
      description: "A card container",
    },
    Metric: {
      props: z.object({
        label: z.string(),
        value: z.string(),
        format: z.enum(["currency", "percent", "number"]).nullable(),
      }),
      description: "Display a metric value",
    },
```

*From the json-render README (Apache-2.0), read 21 November 2026.*

Notice the `description` strings. They are not validation. They are written for the model to read, a point that matters later.

The Vercel AI SDK takes a smaller step. Its docs define generative UI as "the process of connecting the results of a tool call to a React component." The model picks a tool, and developer code decides which component renders the result.

### The agent triggers an interface a developer shipped

MCP Apps is often grouped with the above, but it works differently. A tool declares a `ui://` resource, written by the tool's author ahead of time, and the host renders it. The model decides to call the tool. It does not write the interface. The spec is marked "Stable (2026-01-26)," web hosts typically use a sandboxed iframe, and the app talks to the host over JSON-RPC.

The control here is a sandbox and a content security policy, and the spec has the host build the policy from the domains an app declares. It protects against untrusted app code reaching the host. It is not a check on a model's output, because a model did not produce the HTML. A2UI's docs describe a model-supplied variant, where generated HTML runs as an MCP App inside an A2UI surface. That one is a different case.

AG-UI is not one of these. Its docs say "AG-UI is not a generative UI specification." It carries events between an agent and a front end, and says it supports A2UI, MCP-UI and Open-JSON-UI.

### The agent operates components that already exist

UI SDK's "Connect an Agent" feature lets an agent read and act on a page, but only on UI SDK components registered with its bridge:

```tsx
import { createAgent } from "@ui-sdk/react/agent"

const agent = createAgent()

export { agent }
```

*From the UI SDK docs, Connect an Agent.*

`agent.snapshot()` lists the registered components with the actions each supports, and `agent.act()` runs one:

```tsx
const result = await agent.act({
  steps: [{ ref: "Project name", action: "setValue", args: ["Atlas"] }],
})
```

*From the UI SDK docs, Connect an Agent.*

Nothing here generates a new interface. The risk is different: an agent that can change values and press controls. The control is a permission layer. An `allow` callback runs before each step and can refuse it. A control marked `data-agent-confirm` is meant to need a person, but the docs add a warning that undercuts it: "An `allow` that returns `true` without reading `step.confirm` answers yes for the person." Components can be hidden from the agent with `data-agent-hidden`, and values redacted with `data-agent-secret`.

The tools are marked with `untrustedContentHint`. The docs say tool results can include text your users wrote, which is the route by which page content can steer an agent.

### The agent writes the code

The fourth case happens before anyone opens the app. UI SDK also ships a headless library of behaviors (focus, selection, popups, ARIA) and a skill for coding agents:

```
npx skills@latest add vercel-labs/ui --skill ui-sdk
```

*From the UI SDK README.*

Here the controls are tests and code review, and UI SDK's AGENTS.md describes testing helpers that check components against WAI-ARIA patterns. That is a structural accessibility check on what the agent built.

|---|---|---|---|---|
| Generate from a catalog | Catalog and function permissions; the app developer | Model picks something not allowed | Which components and functions, and the shape of props | Whether values and content are right. The A2UI pages read describe no semantic check *(not found)*. The docs say the model can update the data model *(documented)* |
| Trigger a shipped UI (MCP Apps) | Sandbox and CSP; the host enforces, the tool author writes the HTML | Untrusted app code | What the app's code can reach | Whether the author's UI is accurate or accessible *(my reading)*. Docs: "Host support varies by client" *(documented)* |

| Write the code | Tests and review; the team | Broken or inaccessible components | Structure, ARIA patterns, behaviour | Whether the product logic is right *(my reading)* |

The tags show the evidence class per cell. Vendors have drawn their own maps: CopilotKit's spectrum, AG-UI's categories and a community list each sort by how much freedom the agent has. That axis is different from this one, which asks what is checked. One vendor page announces three pillars and shows four bands, so treat these as marketing taxonomies, not standards.

## What the controls leave open

### The documents say so themselves

json-render's documentation for its experimental composer says "Completion is not a correctness guarantee," and warns that registering an action does not make it safe to run with arbitrary values: authorize and validate requests in your handler as usual. UI SDK's permissions page has a section on what `allow` covers, and lists the gaps. A2UI's docs say the app developer controls what the agent "can and cannot do." Control of form and authority is what is offered, and on this point the vendors mostly do not claim more.

The checks that do run on values are documented for a different purpose. A2UI's `@checks` attach to input components, and its `regex`, `required` and `email` functions are documented for input validation: fields a person fills in, not content an agent authored.

### One claim goes further than the docs

A2UI's announcement says its server-side binding means "sensitive values never reach the model." The docs support part of it: server code can inject data into a surface without passing it through the model. But button actions send resolved values to the agent, `sendDataModel` attaches the full surface data model to every message to the agent that created the surface, and the docs say the data model can be updated by the language model during generation. They do not say whether data sent to the agent's server then reaches the model. Whether a given value reaches the model depends on how you build it, and nothing read here turns that into a guarantee.

### The boundary and the model are not separate

It is tempting to treat this as a contest between the boundary and the model. The json-render catalog above shows why it is not. Its descriptions steer the model, so a catalog with poor descriptions fails with a good model and a good catalog is wasted on a weak one.

A more useful division is worst case against typical case. A boundary caps the worst case, what can appear and what can happen. The model, and any checks you add, set the typical case: whether the choice and the values are right. An agent that picks a registered component and fills it with wrong values has stayed inside every boundary on the map.

## Where content does get checked

If the claim is wrong, it should be easy to disprove: find a documented runtime control that checks content correctness. The search for one found a partial counterexample and several leads.

A2UI ships an eval framework. Its roadmap lists, as available today, "an eval framework that scores the project datasets with schema checks, assertions, and an LLM judge." The design document describes three stages: schema and structure; deterministic assertions such as required components and bindings; and an LLM judge that grades the payload against a rubric written for each sample. That last stage is a content-level check. It runs offline on the project's own datasets, and with the judge switched off, the scorer passes any sample that cleared the first two stages. A "tool usage as a judge" feature is on the roadmap, not shipped.

Two more routes exist, and both are yours to build. A2UI's agent-side functions run on the server, and its docs give examples such as checking live seat inventory or verifying a booking code. AG-UI lists interrupts, a way to pause for a human to approve, edit or retry.

Offline benchmarks of generated UI also exist, some run by competing vendors. They were not read beyond summaries and are not relied on here.

So the picture is this. The runtime controls check form and authority. Content is checked offline, by judges and humans, and by code you write. The documents read describe no runtime gate that does it for you.

## The cost of leaning on the boundary

Three costs come with the controls themselves.

**Prompt injection.** An agent that reads page content can be steered by it. UI SDK marks its tools as handling untrusted content, and `allow` and confirmations are the response, but they depend on the policy you write and on a person reading the prompt.

**Enforcement location.** `allow` and `data-agent-confirm` run in the page. Authorization that matters still belongs on the server the controls call. This is my reading. The docs do not discuss it.

**Version drift.** A2UI's protocol is 1.0, and its released packages are 0.x, which the release notes show implementing it: the Python agent SDK was 0.12.0 on 17 November, a week after 0.11.0. The costs sit in the consumers. The announcement says Gemini supports 0.9.1 today, the Jetpack Compose renderer is at 0.9.1, and ByteDance's Lynx renderer is adapting. The evolution guide says catalogs written for 0.9 "cannot be used directly" with 1.0. If your catalog is your boundary, it has a migration cost.

Add the usual risks of young projects. UI SDK's README says "UI SDK is in beta," with 0.1.0-beta.13 out on 19 November. The AI SDK's RSC route is "currently experimental." Tambo's README opens with "Tambo Cloud is shutting down." I found no independent evaluation of reliability, accessibility or security for any of these in the sources read.

## The objection

The strongest objection is that this is least privilege restated. Anyone who has put validation and permissions around a non-deterministic component already believes controls should be narrow and content should be checked separately. Fair. The new part is the map: what each documented control checks, where the vendors say it stops, and which claims go further than the documents.

Another objection is that absence from the pages read is not absence from the field. Also fair, and it is why the claim is phrased as falsifiable. One documented runtime content check would break it.

The last is that a thin boundary might argue for spending effort elsewhere. It might. That is a judgment about where your effort belongs, and it is exactly what the controls above leave to you.

2. **Who owns it?** A catalog you maintain, a sandbox the host enforces, or a callback you write?
3. **Where is content checked?** Offline evals, a human, a server-side function, or nowhere?
