# Technical Review

Reviewed: `drafts/v1.md`, against `research.md`, `sources/sources.yaml` and live primary pages re-read on 2026-11-21 (a2ui.org concepts pages, A2UI releases and evolution guide, ui-sdk.dev docs and the `vercel-labs/ui` README, AGENTS.md and SKILL.md, MCP Apps overview and the 2026-01-26 spec, docs.ag-ui.com, ai-sdk.dev, json-render README, Tambo README, assistant-ui docs, CopilotKit spectrum page). "Dossier" means `research.md`. Page-reading was done through a summarising fetch tool for most pages, so exact wording should still be re-copied before publication.

## Critical issues

1. **MCP Apps is filed under "Emit: the agent produces the interface" and "Unconstrained emitters", but its UI is not produced by the agent at runtime.** Sentences: "In the first job, the agent produces what appears on screen, at runtime", "Unconstrained emitters", and "The agent, or the tool author, is not picking from a catalog. It is shipping an interface." The MCP Apps overview says a tool's description carries `_meta.ui.resourceUri` pointing at a `ui://` resource that "the host can preload ... before the tool is even called". The spec says the resource is predeclared and "MUST exist on the server", and the hosts may prefetch and cache it. So the HTML is authored by the MCP server developer ahead of time. The model only decides to call the tool and supplies inputs; the host pushes tool results into the app. CopilotKit's own page (cited in the draft) calls these "3rd-party surfaces". This matters because the "sandbox is the boundary for unconstrained emitters" half of the thesis assumes a model-generated artefact. For MCP Apps, the party being sandboxed is a third-party developer, and the relevant risks are supply-chain and tool-author trust, not model output. The "agent, or the tool author" hedge does not fix it, because the section heading and opening sentence state the agent as the producer. Checked: MCP Apps overview, spec 2026-01-26 (via fetch), CopilotKit page. A2UI's note that "generated HTML and JS can run as an MCP App inside an A2UI surface" shows a different case (model-supplied HTML); the draft mixes the two cases without distinguishing them.

## Major issues

1. **"Stable" paragraph infers a contradiction the sources do not show.** Sentences: "The released packages tell a different story", "None of the releases ... is a protocol release", and "the evolution guide says catalogs written for 0.9 'cannot be used directly' with 1.0". (a) The package versions (agent SDK 0.12.0, CLI 0.4.0) are SDK semver, independent of the protocol version. The release notes I read mark entries as "(v1_0)" or "(v1.0)", for example a2ui-core 0.7.0 and agent-sdk 0.12.0, meaning the 0.x packages implement protocol 1.0. A 0.x SDK does not contradict a stable 1.0 protocol. (b) The evolution-guide line is under "Breaking changes from v0.9 to v1.0". It is a migration note, and breaking changes at the 1.0 boundary are normal. It says nothing about stability after 1.0. (c) The draft's valid point is the consumer lag (Gemini 0.9.1, Compose 0.9.1, Lynx adapting), which is stated by the announcement. The dossier's "Contrary evidence" did not note the "(v1_0)" release-note labels, so the draft inherits the gap. Checked: A2UI releases page, `evolution_guide.md` line 201, announcement.

2. **The "Operate" job is described more broadly than the evidence supports.** Sentences: "an agent that can press buttons on your page", "Every control the page exposes becomes something an agent can try", and "an agent reading and operating components that are already rendered." The `createAgent` bridge "connects an agent to the ui-sdk components in your app" (ui-sdk.dev connect-an-agent). It only sees and acts on UI SDK components, and a snapshot lists at most 100 components. It is not a general page-operating agent (no DOM or accessibility-tree agent, no arbitrary controls). Both the risk statement and the "permission layer is the boundary" claim generalise from one beta library's design. Checked: ui-sdk.dev/docs/agents/connect-an-agent.md.

3. **Permission mechanics are overstated in places.** Sentence: "A control marked `data-agent-confirm` always needs a person". Per the permissions page, without `allow` the press fails and asks the person to press it themselves; with `allow`, "the step waits for your callback", and a callback returning `true` answers for the person. The draft quotes that warning two sentences later, so the two statements conflict. Also unstated: with no `allow` callback the bridge accepts supported actions (dossier Claim 6, S3; the permissions page I read confirms that `allow` is the only gate for non-marked controls). Sentence: "a step fails if nobody answers within five minutes" omits that 5 minutes is the default and `timeout` on `createAgent` changes it. Checked: ui-sdk.dev permissions page.

4. **"None of them judges content" and "How will you test accessibility ... The boundaries above do not" contradict what UI SDK ships for the "Write" row.** Sentences: "All four boundaries limit form or action. None of them judges content." and question 6 of the checklist. The Write boundary in the draft is "tested behaviors, tests, code review". UI SDK ships `@ui-sdk/core/testing`, which checks the result "against its WAI-ARIA pattern, in right to left and on the server" (AGENTS.md), and the skill requires contrast checks (4.5:1 text, 3:1 control edges) in a real browser, plus an agent-ready test (SKILL.md). That is an accessibility boundary, which is also what the thesis claims boundaries settle. The statement holds for catalogs and permission layers but not for all four. Checked: AGENTS.md, SKILL.md, agents.md on ui-sdk.dev.

5. **The boundary map presents the jobs as separate rows when the sources show them overlapping inside single products, and some row assignments are weak.** (a) UI SDK sits in both "Write" and "Operate". The skill's mandatory step 3 is "Make it agent-ready" with `createAgent`, so the agent that writes the component is expected to make it operable. The draft treats these as two jobs, which is fair, but never says that the product couples them, and the "Operate" section opens as if it were an unrelated feature. (b) AI SDK tool UIs are placed in "Emit, constrained / component catalog". In the AI SDK docs the model emits a tool call, the tool's `execute` returns data, and developer code spreads `part.output` into a component's props. There is no catalog and the model does not emit UI structure. The AI SDK page itself says to validate that shape before rendering. The boundary is tool schema plus developer code. (c) The same A2UI catalog can include a component that hosts MCP Apps or arbitrary HTML (a2ui.org homepage and the "MCP Apps in A2UI" guide), so "Which components can appear" does not bound content for such a catalog, and the catalog boundary becomes the sandbox boundary. The objection section mentions the blur but the table does not. (d) The "What it limits" cell for A2UI omits function permissions (`allowedCallers`, `agentOnly`), which the draft describes in prose. Checked: ai-sdk.dev generative-user-interfaces, a2ui.org, SKILL.md.

6. **The MCP Apps boundary is described incompletely, and one default is misleading.** Sentence: "sets a restrictive default (`default-src 'none'`, `connect-src 'none'`)". The spec's default CSP also includes `script-src 'self' 'unsafe-inline'` and `style-src 'self' 'unsafe-inline'` plus `img-src`/`media-src` `'self' data:`. Inline script is permitted by default. The draft also omits that the spec requires the outer sandbox to have `allow-scripts` and `allow-same-origin`, which is why the different-origin MUST exists. The table cell "What the HTML can reach" omits the host-mediated channel: an app "can call any tool on the MCP server", send messages, and update the model's context, and can request `permissions` (camera, microphone) via `_meta.ui`. That channel, and the host's decisions about it, is a large part of the real boundary and the main route by which app content reaches the model. Checked: spec 2026-01-26 (via fetch), MCP Apps overview.

7. **The "Where the claims outrun" "Sensitive values" paragraph cites the wrong page and leaves out the second route.** Sentence: "The messages page also says the data model 'can be updated directly by the language model during generation.'" That sentence is on the data-binding page (`a2ui.org/concepts/data-binding/`). It is not on the messages page (grep of the page found no match). The dossier made the same attribution (S5 is aggregated), so the error propagated. Content verified otherwise: `sendDataModel` attaches the full data model to "every outbound message", server code can inject "without passing them through the model".

## Minor issues

1. **Skill install command differs from the page it is attributed to.** The block "npx skills add vercel-labs/ui --skill ui-sdk", captioned "From the UI SDK README", is `npx skills@latest add vercel-labs/ui --skill ui-sdk` in the README and in the docs (docs.md, agents/skills.md). Without `@latest`, an older cached skills CLI may be used. Checked: raw README.
2. **"never generate ids" mistates a styling rule.** The skill's rule is under "Style from state": "Never inline styles for state, and never generated ids", meaning do not target generated ids in styles. The draft turns it into a generation rule ("never generate ids"). Checked: SKILL.md.
3. **"The agent composes them" and the described skill workflow ("define a primitive") blend two paths.** SKILL.md says "Most interfaces only need path 1" (compose shipped components). "Define a primitive" belongs to path 2 (components UI SDK does not ship), and the skills docs page describes the skill as for components "ui-sdk doesn't ship". Say which path the described workflow is.
4. **UI SDK launch date.** "The next day, Vercel Labs introduced UI SDK" rests on a single docs changelog entry ("Introducing UI SDK", 2026-11-12) and the dossier's inference. The README gives no launch date, and the first beta was dated 11-13 per the dossier. I could not find an announcement page. Mark as inferred or soften.
5. **"marked `root`"** is imprecise. In A2UI 1.0 the root is the component with `"id": "root"`, and `updateComponents` must include exactly one such component. `createSurface` in 1.0 can also carry the initial `components` and `dataModel` in one message, which the draft's description ("creates a surface, sends components") hides.
6. **AG-UI "it carries the formats above".** The AG-UI docs say it carries A2UI, MCP-UI/MCP Apps and Open-JSON-UI and allows custom standards. They do not claim json-render, assistant-ui, Tambo or AI SDK formats. "The formats above" overreaches. The docs list MCP-UI and the README MCP Apps, a naming inconsistency the dossier recorded and the draft does not.
7. **"the host renders the HTML it contains in a sandboxed iframe".** The overview says "Web hosts typically render the HTML inside a sandboxed iframe". Rendering in an iframe is the web-host case, not a requirement for all hosts.
8. **Table, Operate row.** The boundary listed includes `data-agent-hidden` and `data-agent-secret`, but the "does not cover" cell describes only `allow`'s gaps ("components remain in `snapshot()`"). Components inside `data-agent-hidden` are left out of `snapshot` and `query`, so the cell is true only for unmarked components. The draft says this itself in prose; the cell should say "unmarked".
9. **Tambo fairness.** The draft says the project "remains open source and self-hostable" (verified in the README) but omits that Tambo's own post (S17, 2026-10-01) says the team is pivoting to Charming, which bears on maintenance. Also, the user-data deletion date (2026-11-30) is nine days after the reading date.

## Unsupported claims

1. **"There are 55 unstyled React components built on it."** The README does not state a number. The ui-sdk.dev docs I could fetch did not state it. It comes only from the dossier (S2) and I could not verify it. "Unstyled" is also qualified by the optional `@ui-sdk/core/web.css` default look (SKILL.md).
2. **Quote "UI SDK is in beta, so some APIs may still change".** The README says "UI SDK is in beta" and "the framework, APIs, documentation, and behavior may change before general availability" (via fetch). I could not find the quoted wording on the pages I read. Dossier attributes it to docs. Re-copy or paraphrase.
3. **"every release so far is a pre-release".** I confirmed that the three newest releases (beta.13, beta.12, vue beta.13, 2026-11-19) are pre-releases through the GitHub API. The dossier says it read "the first releases page only". "Every release so far" is not established.
4. **"I found no independent evaluation of the reliability, accessibility or security of generated interfaces for any of these projects."** An absence claim. I could not verify it, and one search pass is thin. Rephrase as "none were found in the sources read".
5. **Interpretive statements stated as fact**: "Writing code with an agent is the familiar kind of risk, and it comes with the familiar controls", "A sandbox ... says nothing about whether the interface it renders is accurate or accessible", and "Its rules are the unglamorous kind that decide whether generated UI is usable". These are author inferences, and the last is an opinion about the rules; none appears in a source. The article marks two table cells as "my reading" but not these.
6. **"Operating a live page is cheap to add".** No source gives an integration cost. UI SDK's own benchmark (vendor-reported, one task, medians of three runs) concerns agent efficiency, not adoption cost. Could not verify.

## Missing trade-offs

1. **Prompt injection and untrusted content.** The WebMCP tools carry `untrustedContentHint` on all three tools because "results include page content". MCP Apps can send messages and update model context. Neither the Operate nor the MCP Apps part says that page or app content is an injection path into the model, which is the central risk of "an agent that can press buttons". The draft's trade-offs cover only the "content is wrong" case. (Sources: WebMCP page, MCP Apps overview.)
2. **Client-side enforcement.** `allow` and `data-agent-confirm` run in the page, in the same trust domain as the page code. They are a UX confirmation layer. Real authorisation still has to be enforced by the backend that the controls call. The draft calls this layer "the boundary" without saying what it does not prevent. (My analysis; the docs do not discuss server-side enforcement. They also say the hints are not restrictions: "they don't restrict anything".)
3. **Supply chain for the Write job.** Installing a skill with `npx skills@latest add` puts third-party instructions into the coding agent's context, and the skill tells the agent to read installed docs. That is a trust boundary of its own, and the draft's Write section lists only review and tests.
4. **Operate alternatives.** The draft does not compare the semantic-bridge approach with other ways an agent operates a UI (DOM or accessibility-tree browsing agents, screenshot-based computer use, AG-UI frontend tools and interrupts for human-in-the-loop, which the AG-UI nav shows). Without that, the claim that Operate "gets the least attention" and is "UI SDK's" is weak. Could not verify the claim about attention.
5. **Constrained emit: runtime costs.** The A2UI SDKs validate agent output against surface state and return errors to the model (dossier Claim 4), so a failure mode is a retry loop. Catalog size also costs prompt tokens (json-render and Tambo both turn Zod schemas into tool definitions). Neither appears in "Trade-offs".
6. **Accessibility of emitted UI.** For constrained emitters, accessibility depends on whether the renderer components are accessible. For MCP Apps, it depends on the HTML the server author wrote, inside an iframe the host cannot inspect. The draft says only "says nothing about whether ... accessible".

## Missing constraints

1. **UI SDK `createAgent` constraints**: applies only to UI SDK components; caps the snapshot at 100 components; React 19+ is required for the React package (docs.md quick start); `setValue` calls the component API directly, so checks in keyboard or pointer handlers do not run (dossier Claim 6, S3; I did not re-confirm this sentence). A canceled value change can return `ok: true` with no change, so `values` must be checked (permissions page, verified).
2. **A2UI renderer and catalog negotiation.** A surface names a `catalogId`, the agent and renderer must support the same catalog and protocol version, and an agent on 0.9.1 (Gemini) cannot target a 1.0-only renderer. The draft notes version lag but not that a mismatch is a runtime failure mode.
3. **MCP Apps host variance.** Overview: "Host support varies by client." The client matrix was not read (dossier). The draft lists hosts but not that features such as permissions, CSP enforcement and tool-call proxying are host-controlled and vary.
4. **json-render's constraint mechanism is undocumented.** The README says "Guardrailed" and "JSON output matches your schema, every time", but the dossier records that how the model is constrained (structured output, constrained decoding, or prompt plus validation) is not described. The draft quotes "constrained to components you define" without saying the enforcement mechanism is unknown. Also, the README quick-start's registry example calls an undefined `format()`; the draft shows only the catalog block, which is accurate as a copy.
5. **WebMCP has no linked specification** in the UI SDK docs (dossier Claim 6) and no named supporting browsers. The draft says the second half but not that the API surface (`document.modelContext.registerTool`) is unspecified in the sources.
6. **Tambo hosted API status after 31 October** was not checked (dossier). The draft's "was due to stop" is correct; add "I did not check whether it did".

## Recommended changes

1. **Re-classify MCP Apps.** Describe it as developer-authored, pre-declared UI that the agent triggers, or split the "emit" family into "agent generates the interface" and "agent selects a developer-shipped interface". Revisit the opening of "Emit" and the table row. Keep the A2UI-embeds-generated-HTML case as the genuinely model-supplied HTML example. (Critical 1)
2. **Rewrite the "Stable" paragraph.** Separate protocol version from SDK package versions, say that the 0.x packages implement v1.0 per their release notes, and drop or reframe the evolution-guide line as a 0.9 to 1.0 migration break. Keep the consumer-lag point (Gemini, Compose, Lynx). (Major 1)
3. **Scope the Operate claims** to "UI SDK components registered with the bridge", cite the 100-component snapshot limit and the default-open behaviour without `allow`, and remove "every control the page exposes". (Major 2, 3)
4. **Correct the permissions description**: `data-agent-confirm` requires a person only when `allow` does not answer for them; 5 minutes is a default. (Major 3)
5. **Fix "none of them judges content"** to exclude or qualify the Write row, which includes accessibility testing, or move accessibility out of the claim. Adjust checklist question 6 accordingly. (Major 4)
6. **Revise the boundary table**: reposition AI SDK tool UIs or add a note, name function permissions for A2UI, add the A2UI-embeds-HTML case to the "Emit, constrained" last column, add the host-mediated channel and `'unsafe-inline'` default for MCP Apps, and qualify the Operate "visibility" cell with "unmarked". (Major 5, 6; Minor 8)
7. **Correct the page attribution** of "can be updated directly by the language model" to the data-binding page. (Major 7)
8. **Re-copy code and quotes from live pages**: skill command with `@latest`, the "beta" quote, and the SKILL.md "ids" rule. Remove or source the "55 components" figure. (Minor 1, 2; Unsupported 1, 2)
9. **Add trade-offs**: prompt injection via page content and app messages, client-side nature of `allow`, skill supply chain, alternatives for Operate, validation-retry and prompt-size costs for emitters. (Missing trade-offs 1 to 5)
10. **Mark author inferences** ("familiar kind of risk", "cheap to add", "unglamorous kind") as such, or delete them, and rephrase the "no independent evaluation" sentence as limited to the sources read. (Unsupported 4, 5, 6)
11. **Soften or qualify** the UI SDK launch date, the "every release" wording, the AG-UI "formats above" wording, and the iframe sentence for MCP Apps. (Minor 4, 6, 7; Unsupported 3)
