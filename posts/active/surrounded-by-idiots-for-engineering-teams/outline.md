# Outline

## Article

What "Surrounded by Idiots" Gets Right (and Wrong) About Communicating on
an Engineering Team

## Structure

### Hook / Problem

Open on a specific, recognizable engineering moment where a
communication-style mismatch (not a technical disagreement) caused real
friction — a terse code review comment read as an attack, a quiet
teammate's objection skipped in standup, a decisive engineer quietly
labeled "difficult" in design review. Do not open with the book itself.

- [AUTHOR EXAMPLE] a specific real moment like this from the author's own
  team, if available — stronger than a generic composite.

### Observation

Name the pattern: these recurring frictions are style collisions dressed
up as technical disagreements. Bridge to why a popular book (*Surrounded by
Idiots*) became a go-to reference point for naming this — its reach (55
languages, 1.5M copies) is evidence people are reaching for *something*
here (research.md Claim 5).

### Thesis

State the thesis plainly and early: the four-color framework is
scientifically weak, but it's still a useful shared vocabulary for a
narrow, specific reason — and that reason has nothing to do with the
taxonomy being true.

### Evidence — the science, stated precisely

- DISC's real lineage (Marston, 1928) and its Red/Yellow/Green/Blue mapping
  (Claim 1).
- The precise, defensible critique: decent test-retest reliability
  (.71–.89) but no demonstrated predictive validity; possible reducibility
  to Big Five traits (Claim 2). State this exactly — reliable-but-not-valid
  — not a blanket "it's made up."
- Direct, named criticism of this specific book (Umeå University
  psychologist; "Fraudster of the Year" award) (Claim 3) — [AUTHOR OPINION]
  needed on whether to name the book/author/award specifically vs. discuss
  DISC-style frameworks more generically (research.md's flagged judgment
  call).

### Framework or Architecture — what actually does the work

Introduce Google's Project Aristotle finding as the validated comparison
point: psychological safety ("how the team interacts," not who's on it)
is the actual, evidence-backed lever (Claim 4). Make the mechanism
argument explicit: a shared vocabulary lowers the cost of naming a
mismatch in the moment — the DISC labels are a low-stakes on-ramp to that
same behavior, not a competing, more-scientific alternative.

- State the one real evidence gap plainly: no source directly tests
  whether a shared-vocabulary tool itself changes outcomes, distinct from
  psychological safety generally (research.md Open Questions). Don't paper
  over this.

### Concrete Examples

Map the framework onto 2–3 specific engineering scenarios, each showing:
the style collision, how a color-coded label makes the mismatch nameable,
and the mitigating discipline (label the interaction, not the person).

1. Code review feedback (bluntness read as attack)
2. Incident retro turn-taking (a quieter engineer's read gets skipped)
3. Design review disagreement ("disagree and commit" moments)

- [AUTHOR EXPERIENCE] at least one of these should be a real instance from
  the author's own team, not a generic hypothetical.

### Trade-offs

What you gain (a low-stakes shared vocabulary, faster naming of a
mismatch) versus what you risk (permanent labeling, stereotyping,
"that's just how reds are" as a conversation-ending move — the exact
failure mode named in Argument 3 / the Response). Be concrete about what
mitigates the risk (situational framing, pairing a label with a specific
behavior, never letting it end a disagreement).

### Counterargument

State the skeptic's case in full, undiluted (from thesis.md) — this is not
a strawman pass. Then the Response: concede the science, narrow the claim
to the shared-naming mechanism, name the stereotyping risk as the real
failure mode rather than defending against a weaker objection.

### Recommendation

A concrete, practical recommendation for a team lead: if you want this,
adopt it narrowly (a shared vocabulary + explicit ground rules against
using it to end an argument), and treat validated practices (structured
retro formats, explicit psychological-safety norms) as the foundation, not
this framework.

- [AUTHOR OPINION] needed: how far to push this — "useful on-ramp, adopt
  deliberately" vs. "arguably skip it entirely and go straight to
  psychological-safety practices."
- [AUTHOR EXAMPLE] a specific practice the author has used (a "how I like
  feedback" doc, a team agreement, a specific phrase for flagging a
  mismatch).

### Conclusion

Return to the opening scenario; show it resolved (or note what a
resolution would look like) using the narrow, disciplined version of the
tool rather than the book's uncritical framing.
